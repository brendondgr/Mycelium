# EXP-2026-11-022 — Results

## 1. Headline

Replaying the 2026-11-15 code (`44100c04`), unchanged, against today's Gemma 4
31B server (`vllm-0.21.0-5c6ca01c`, the 11-17 server) reproduced the blank
turns: **19 of 108** (17.6%; 11-15, same 108 asks: 21 of 108). The same code
with its model calls sent **unstreamed** gave **0 of 108** blank turns and 0
empty calls in 700, so the blanks are the server's streamed function-call
parsing dropping a short call. 11-17 code (`55cfdb1c`) still meets the drop
(14 of 108 turns) but repairs it, so **0 of 108** were blank: on 11-17 the
server had not changed; our code had learned to recover (`a8e21c0e`).

## 4. Interpretation

**What the empty call is.** Every empty call in `f1115` (39) and `f1117` (28)
follows a function result, comes back with `finish_reason: tool_calls`, 13
completion tokens (twice 9) and no text and no call: the server says the
model called a function and hands none back. The stored 11-15 threads have the
same signature (13 or 9 tokens, after a function result, `empty_retry`). The
diagnostic request beside each (same messages, `tool_choice: none`, special
tokens kept) shows in 39 of 39 and 28 of 28 a single argument-less call in
Gemma's own markup, e.g. `<|tool_call>call:projects_list{}<tool_call|>`
(`projects_list`, `files_list`, `me_profile`). These calls are not wrong:
the same 13-token calls after a function result were read correctly 103
times in `f1115` (39 dropped of 142) and 89 times in `f1117` (28 of 117),
including calls to functions the request did not offer, and **133 of 133**
when unstreamed (`f1115ns`). The model call's own identical retry was empty
again in 19 of 20 cases in `f1115` and 14 of 14 in `f1117`, so for a given
request the drop is close to deterministic. Our reading: vLLM 0.21.0's streamed Gemma 4
call parsing loses some short argument-less calls that the same server's
unstreamed parsing reads; what decides which is not visible from here.

**Why 11-15 and not 11-17.**
1. **Not a server change, as far as this run can show.** Today's server
   (fingerprint identical to 11-17's) reproduces the 11-15 rate with the 11-15
   code (19 vs 21 of 108). The 11-15 server's build is not recorded, so it
   cannot be shown identical; it is not needed to explain the difference.
2. **Our code changed how a dropped call ends.** At `44100c04` an empty reply
   got only the identical retry, which is empty again, and the empty text was
   posted. `a8e21c0e` (2026-11-15 10:58 EST, hours after the 11-15 runs) adds
   a retry without functions and the give-up line. On the 016 asks the 11-17
   code still meets the drop in 14 of 108 turns (20 at `44100c04`): 12 then
   answered, 2 ended on the give-up line, 0 blank (at `44100c04`: 19 of the 20
   blank, 1 answered). EXP-2026-11-019 r4–r6
   counted 0 blank *by construction* of that repair; its "empty model calls"
   column is the measure to compare.
3. **The 11-17 asks rarely made such calls.** EXP-2026-11-019 r4 (S1, S2,
   S10) made 8 calls of 17 completion tokens or fewer after a turn's first step,
   in 939 (`model_call_log` of its two r4 files);
   the 016 probes make about one in five calls of that kind (142 of 669).

**What this run does not explain.** EXP-2026-11-019's round-two blanks (11-15)
were mostly a different shape: read from its kept database
(`mycelium_sandbox_exp019`, both arms), 48 of its empty steps were the **first** step of
a turn (51, 35 or 22 completion tokens) and 8 followed a function result (13
tokens). The 11-17 empty calls (EXP-2026-11-019 Amendments 7, 8) are that
first-step shape (`finish_reason: tool_calls`, 35–51 tokens), at 3–4 in about
950 calls, against most of round two's 49 blank turns. Whether the first-step
drop is the same streaming defect, and why its rate fell between 11-15 and
11-17 (code, recall, harness or server), is not tested here: replaying 019's
round two needs its three repetitions (the rate rose 5 → 19 → 25 of 103 with
them), about 300 turns.

Claims: C-055 (no blank turn since `a8e21c0`) is consistent: `f1117`, 0 of
108. No claim changes status.

## 5. Threats to validity

- Instance settings (`.env`, `mycelium.toml`) are today's; the 11-15 values are
  not recorded (ISSUES.md §1). The 11-15 rate was reproduced anyway.
- The diagnostic text is a fresh sample, not the dropped text (ISSUES.md §3);
  the 13-token match and the unstreamed parse are the supporting evidence.
- Unstreamed vs streamed was varied on the 11-15 code only. That the 11-17
  code's drops are the same defect rests on their identical signature, not on
  a separate test.
- One repetition per cell (108 turns); the 11-15 rate across three
  repetitions was lower (14.5%) than in the first (19.4%).
- Load: 6 in flight from this run; other load on the server unknown. The
  diagnostic request adds one request per empty call (39 + 28).

## 6. What surprised us

That neither the missing arguments nor an unoffered function name explains
the drop: the server reads exactly these calls most of the time, and always
when not streaming. And that the identical retry fails again almost every
time, so retrying the same streamed request can never repair it.

## 7. Follow-ups

- Q-070 / Q-088: the mechanism of the after-a-function-result blank is the
  server's streamed call parsing; a repair that would recover without the
  give-up line is to re-send a reply that ends with `finish_reason:
  tool_calls` and no call **unstreamed** (not done here: no product code
  changed). The operator could confirm the vLLM tool-call parser and chat
  template in use, and whether a newer build fixes streamed Gemma 4 calls.
- The first-step drop (019 round two, 11-17 r4–r6): test streamed vs
  unstreamed on the same asks; and replay 019 round two (three repetitions)
  at `44100c04` if the rate fall from 11-15 to 11-17 still matters.
