# EXP-2026-11-005 — Results

## 1. Headline

With the PubMed papers' own identifiers, the full-text tool retrieved 130 of
`EXP-2026-11-004`'s 200 frozen sample papers (0.65, up from 0.54), and 24 of
the 26 mismatch stops on papers whose ids the repair changes went away (23
became full text). The rate half of the hypothesis holds (≥ 0.60); the
mismatch half is **falsified narrowly**: 4 `identifier_mismatch` remain
against at most 3 predicted, all of them foreign PMCIDs the repair at this
commit did not catch.

## 4. Interpretation

- **The repair, not drift, explains the gain.** On the 45 changed papers the
  same-day stored arm reproduced `EXP-2026-11-004` exactly (19 full text, 26
  mismatches), and the own arm got 42 (0.933 vs 0.422). On the 155 papers the
  repair leaves alone, `EXP-2026-11-004` had 89 full text and this run 88 —
  one paper went to abstract-only, the only drift.
- **PMC was the source that was being blocked.** 40 of the 42 changed papers
  came from PMC, which became the largest single source (0.34 of the sample,
  from 0.235). Papers with a PMCID retrieve at 0.933 once the PMCID is their
  own (0.64 before).
- **All 45 changed papers are PubMed-sourced**, matching the scraper as the
  cause. Of `EXP-2026-11-004`'s 28 mismatches, 26 were on those papers; the
  other 2 are OpenAlex rows.
- **The 4 left are foreign PMCIDs nobody's reference list shows any more.**
  Two PubMed rows (PMIDs 42409947, 42400619) have no PMCID of their own and
  keep one that PMC's ID converter assigns to another PMID; the article's
  current reference list no longer contains it (PubMed has rewritten the
  references since the scrape), so the reference-list rule kept it. Two
  OpenAlex rows (PMIDs 42371035, 42446675) have the right DOI and PMID but a
  PMCID absorbed at ingest from a bad PubMed record. Commit 4d27303 adds an
  ID-converter check to `repair_pubmed_ids`; on those four rows it clears the
  two PubMed PMCIDs and sets the OpenAlex ones to the PMID's own (one has
  PMC13694320, one none). That they then fetch is a prediction, not a
  measurement.
- **Corpus scale (Q-057's second half).** The dry run of the improved repair
  on the live database on 2026-11-08 checked 14,657 papers with a PMID and
  would change 7,906 rows: of 12,249 PubMed rows, 3,743 get their own DOI in
  place of a cited paper's, 3,780 a replaced PMCID, 3,159 a PMCID they lacked,
  627 lose a foreign PMCID (423 shown foreign only by the ID converter), and
  3,748 a new `external_id`; 205 OpenAlex/Semantic Scholar rows get their own
  PMCID back. 205 corrected DOIs already sit on another row — duplicates the
  bad DOI hid, for `dedupe_content_papers` to merge. No `external_id`
  collisions, and no other-source row carries a citing paper's PMID. These
  counts are from the command's output, not this run's `metrics.json`.

## 5. Threats to validity

- **Simulated, not applied, repair.** The run corrects ids in memory with the
  repair's own decision code; it did not read a repaired database. The live
  repair writes the same values for the sampled PubMed rows, but this run
  does not test the write path (its tests do).
- One sample, one network, one day; "full text" is the engine's own length
  test, as in `EXP-2026-11-004`.
- The repair's dry-run counts are from a live, changing database and were not
  snapshotted.

## 6. What surprised us

That PubMed rewrites reference lists after the fact: a cited paper's PMCID can
sit on a row while the article's current record no longer lists it, so
"is it one of the references?" is not enough to prove an id foreign.

## 7. Follow-ups

- Apply `repair_pubmed_ids` on the live database (operator decision), then
  run `dedupe_content_papers` for the 205 exposed duplicates.
- Re-run this sample on the repaired database to measure the 4 rows the
  improved repair fixes (Q-058).
